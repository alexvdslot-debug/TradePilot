## Architecture choices
Cloudflare Access is the selected authentication provider; user ownership comes
from verified Access identity, not a client-selected account ID. Existing D1 and
same-origin Worker routes are reused. Plain JavaScript ES modules isolate ledger,
valuation, mapping, market quality, journal and alert calculations. Node tests,
SQLite integration tests and Playwright exercise this architecture; no unconfigured
React/Vite/Vitest/typecheck pipeline is claimed. The current implementation and
acceptance boundaries supersede the earlier framework proposal in the
[updated technical plan](TECHNISCH_BOUWPLAN_V1.md).

## Limitations and release blockers
- The owner authenticated the earlier production TradePilot session. New source changes still require their own authenticated release smoke if deployed; this task does not reuse an earlier smoke as proof of changed code.
- `TWELVE_DATA_API_KEY` stays on the existing `tradepilot-market-data` Worker. The app uses an internal `MARKET_PROVIDER` service binding with Access JWT verification on both sides. No secret is read, copied or embedded in source/frontend. The prior quote interface is preserved.
- Account display entitlement remains unverified. The known Basic8/non-display position and generic provider realtime/default-feed documentation do not establish rights to show this account's live market data in the app. Candle schema verification, historical exchange-clock classification and an optional current market-state route are separate from display/realtime/delay/volume entitlement. Genuine live ranking and production alert trigger/delivery acceptance remain blocked until all relevant evidence is verified.
- Stocktwits app connector authorization does not grant credentials or redistribution rights to a deployed Worker. No unsupported Stocktwits website scraping or fabricated corroboration is implemented.
- No broker API or verified DEGIRO-specific CSV layout is supplied. Explicit configurable CSV mapping is implemented, but a real broker export, UTC/timezone conventions, fees/cash reconciliation and actual manual-USD account settings still need owner review. Corporate actions, FIFO/tax reporting, persistent correction/audit history and deposit-weighted historical FX performance remain outside acceptance. Portfolio valuation/concentration/history and linked closed-trade statistics are now implemented locally; their truthful data-quality limits and fixture coverage are documented rather than listing them as absent.
- State is a bounded per-user versioned snapshot (200KB, max2000 events, max500 journal plans, max50 watchlist/alerts). Conflicting tabs receive409 and must reload; no silent merging.
- Shared quota code and additive `0004_provider_quota.sql` are implemented and tested: 8 actual requests per UTC minute and 800 per UTC day, atomically reserved per provider across callers sharing `MARKET_QUOTA_DB`. These safeguards are not provider billing guarantees or a license grant. Deployment must migrate the database and bind every upstream-capable Worker to the same quota store. An absent development binding uses a bounded per-isolate fallback; a configured failing binding rejects requests instead of falling back. Production migration and shared bindings were activated and verified; real upstream calls created the expected shared quota counter.
- Foreground alert configuration/evaluation/read/reset is implemented; verified current-data gates and one-shot provenance are locally exercised. Background/push notification dispatch is not deployed and production alert trigger/delivery is not accepted as complete. No external messages or orders are sent by this implementation.
- WebKit automated coverage is not a physical iPhone acceptance test.

## Safe deployment and rollback
The first release applied `0003_private_state.sql`; preserve its existing owner
snapshot and settings data. The new quota extension adds only
`0004_provider_quota.sql` and requires the shared `MARKET_QUOTA_DB` binding on all
provider-fetch paths. Apply only unapplied additive migrations, never reset D1 or
replace existing account rows. Deploy all Worker modules from the final tested
tree, retain existing secrets/service bindings, and record prior versions before
release. Rollback restores those code versions and leaves additive tables in place;
never drop user data to roll back code. Deployment execution/verification belongs
to the parent release owner and is not performed by this documentation change.

## Lessons
Use true same-origin browser tests with the production security headers. Guard responses from both reads and writes at session boundaries; memory reset alone is not enough to clear already-visible private data. Match browser engines to pinned test dependencies. Safari focus and immediate state reset need browser-specific test actions that do not assume a click leaves a control checked/focused.

Keep historical release evidence distinct from a new working tree. Prefer shared
accounting/market-quality functions over a second implementation, and preserve
unknown provider rights rather than promoting schema-valid timestamps into live
entitlement. Local passing fixtures demonstrate implemented behavior; real broker
imports, current licensed data, deployed background delivery and physical phone
acceptance need their own proof.
